# Thermal validation workflow

Run after installing the repository:

```bash
python analysis/flight_thermal_validation/run.py --output outputs/flight_thermal_validation
```

The default case compares the numerical solver against an **independent analytic dark-cooling solution**. It is a numerical validation, not a flight-validation claim. The checked-in `reference_results.json` was generated by the script: 241 samples, RMSE 0.01381 K, and maximum interval energy-balance residual approximately 1.08e-8 J.

For an observational comparison:

```bash
python analysis/flight_thermal_validation/run.py --telemetry measurements.csv --output outputs/measured_thermal
```

The input needs `time_s`, `direct_solar_w_m2`, and `observed_temperature_k`. Optional `albedo_w_m2` and `earth_ir_w_m2` default to zero. All fluxes must already be projected onto the receiving surface; timestamps and temperature measurements must be aligned. The script records the input SHA-256. It uses the declared `ThermalSurface` parameters in `run.py`; identify those parameters for the observed panel before interpreting the residuals. This runner does not fit them or infer unmeasured irradiance.

Outputs are `thermal_comparison.csv` and `summary.json`, including temperature errors and interval energy conservation. The model is one isothermal node with implicit radiative rejection and temperature-dependent electrical extraction, not a spatial spacecraft thermal model. Related research: [Xie and Li (2026)](https://doi.org/10.1016/j.ast.2026.112268). The implementation does not reproduce that paper's neural model.
